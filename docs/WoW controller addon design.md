# Build WoW controller play on native foundations

A lean controller addon for retail World of Warcraft (Midnight, live client 12.1.5) is very buildable, mostly because Blizzard already ships most of what ConsolePort wraps. Since Shadowlands the client has had a full native gamepad layer: SDL device mapping, `PAD*` binding keys, modifier emulation, an emulated cursor, camera and movement CVars, and Dragonflight-era soft targeting. A small addon can therefore configure the engine instead of reimplementing it. The recommended design is roughly 2-4k lines of Lua with no textures and no idle per-frame code. It has five parts: a one-click setup that writes about a dozen CVars and a binding preset into WoW's own binding sets; an FFXIV-style cross hotbar built as one secure state header that pages 8 secure buttons across three trigger layers using emulated modifiers; a wrap-around party/raid unit cursor for healers; an optional secure utility ring; and Blizzard's Settings panel for options. Profiles live in one account-wide SavedVariables table with per-character and per-spec scoping, plus copy and import/export. The modules this design drops or defers outright hold about 61% of ConsolePort's code by line count, before counting what it trims from the core, rings and targeting modules. They include its 13k-line config UI, its 11.5k-line custom action-bar module, and its art-heavy assets. It also defers the insecure interface cursor, which is ConsolePort's main source of Midnight taint errors. The main risks are Midnight's secret-value and taint rules, which constrain custom cooldown displays and any insecure interaction with Blizzard frames, and the possibility that Blizzard brings WoW: Forever's first-party controller UI to retail. If that happens, the addon's value narrows to targeting, rings and the crossbar.

> **Where the build departs from this plan (October 2026).** The research below still holds; these choices changed once players used it.
>
> - **Own art and config UI.** The plan said no textures and no bespoke config frames. The editor needed a drawing of the pad to be understandable, and the options needed to sit next to it, so LeanPad ships generated controller drawings and command icons and its own settings page. Blizzard's Settings panel stays the entry point. Everything else still uses Blizzard atlases and fonts.
> - **Crossbar is a mirror, not a bar.** Actions stay on Blizzard's bars and the crossbar only displays them, so there are no secure buttons and no override bindings yet. The state-header crossbar described below is not built.
> - **Layer buttons are pure.** As in FFXIV and WoW: Forever, a layer button opens its layer and fires nothing, because the client's tap window would otherwise fire its base action on a short hold.
> - **Play styles** set the combat facing angle and soft-target arcs per role, from the spec. They are not in the original scope.
> - **Not built yet:** profiles and import/export, the healer unit cursor, the utility ring and auto-fill.

## Blizzard's engine already does most of ConsolePort's input work

The decisive finding is that gamepad buttons are ordinary binding keys in WoW. `PAD1`–`PAD6`, the D-pad, shoulders, triggers, stick clicks, stick directions, paddles and the system buttons all appear in Blizzard's binding constants, along with Xbox, PlayStation and Nintendo label styles and ready-made `Gamepad_<name>` glyph atlases ([SharedConstants.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_SharedXML/SharedConstants.lua)). The `C_GamePad` namespace in 12.1.5 exposes device state, configs, LED and vibration. **Only four config-writing functions (`AddSDLMapping`, `ApplyConfigs`, `SetConfig`, `DeleteConfig`) are flagged as restricted**; reading state is open, and it fires events such as `GAME_PAD_CONNECTED` and `GAME_PAD_ACTIVE_CHANGED` ([GamePadDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/GamePadDocumentation.lua)). Modifier emulation is a CVar setting: `GamePadEmulateShift/Ctrl/Alt` turns any pad button into a real modifier. `GamePadEmulateTapWindowMs` lets the same button fire its own binding when tapped. The camera, cursor-click, movement and touchpad families are all CVars too ([ConsolePort Console.lua](https://github.com/seblindfors/ConsolePort/blob/master/ConsolePort/Model/Data/Console.lua)). Blizzard's own UI already switches the gamepad cursor on when bags, loot or the game menu open, through `SetGamePadCursorControl` ([LootFrame.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_UIPanels_Game/Mainline/LootFrame.lua)).

ConsolePort's own README confirms the dependency: "As of Shadowlands, ConsolePort uses native gamepad controls. No external software is required" ([README](https://github.com/seblindfors/ConsolePort)). The bulk therefore sits in what is layered on top. The current suite (v3.3.11) is **nine addons totalling about 59k non-locale Lua lines**, with roughly 15.8k more lines of locale files, about 282 textures and around 29 MB on disk ([repo](https://github.com/seblindfors/ConsolePort)). The breakdown shows where a lean addon saves the most:

| ConsolePort module | Lua lines | Lean-addon verdict |
|---|---|---|
| Core (layers, radial, presets, hints) | 15,188 | Keep a small slice: presets, CLICK buttons, radial |
| Config (settings UI, guide, import/export) | 13,210 | Replace with Blizzard Settings API plus one setup popup |
| Bar (custom action bars, LibActionButton) | 11,510 | Replace with an 8-button, three-layer crossbar or native bars |
| Rings | 3,727 | Keep one ring, drop collections and nesting at first |
| Menu (game menu and unit menus) | 3,486 | Drop |
| Target (raid cursor, unit hotkeys, target ring) | 3,358 | Keep the raid cursor only |
| Cursor (interface node navigation) | 2,932 | Defer; use the native gamepad cursor |
| World (quick menu, loot frame, prompts) | 2,772 | Drop |
| Keyboard (radial on-screen keyboard) | 1,411 | Drop (Steam and OS keyboards exist) |

Line counts are from [the ConsolePort repo](https://github.com/seblindfors/ConsolePort) and its [module registry](https://github.com/seblindfors/ConsolePort/blob/master/ConsolePort/Controller/Modules.lua). Config and Bar together are about 40% of the code. Users are already asking to keep Blizzard's bars: issue #263 requests an "option to not disable blizzard action bars" ([GitHub issues](https://github.com/seblindfors/ConsolePort/issues)). The pain points users report are setup, not missing features: enabling `GamePadEnable`, calibrating, understanding modifiers, and recovering from broken bindings after patches ([Steam Community](https://steamcommunity.com/app/1675200/discussions/0/3186865294573254269); [Blizzard forums](https://us.forums.blizzard.com/en/wow/t/console-port/2214024)). The 2021 ConsolePort wiki still describes mandatory calibration and `/cp recalibrate` ([Wiki](https://github.com/seblindfors/ConsolePort/wiki/1.-Instructions)). Native SDL mapping makes that step unnecessary for known controllers. A lean addon should not ship custom configs, because writing them is a restricted action.

No published CPU or memory measurements of ConsolePort exist. "Less bulky" is therefore measured here in code size, asset weight, SavedVariables surface (ConsolePort uses more than 20 tables across its modules, per its [TOC files](https://github.com/seblindfors/ConsolePort)) and idle per-frame work. It is not measured against a benchmark.

## The cross hotbar maps onto modifier pages, with one honest compromise

FFXIV's cross hotbar is a storage-and-pointer model. Holding LT or RT reveals 8 slots per side (4 D-pad, 4 face buttons), so a "set" holds 16 actions, and there are 8 sets ([Akhmorning: The Cross Hotbar](https://www.akhmorning.com/resources/controller-guide/the-cross-hotbar/)). Expanded Hold Controls (LT then RT, or RT then LT) and WXHB (double-tap a trigger) do not add storage. They are pointers that show "set N, left or right side" ([Official UI Guide: Expanded Hold Controls](https://na.finalfantasyxiv.com/uiguide/know/know-xhb/xhb_hold.html); [Square Enix forum](https://forum.square-enix.com/ffxiv/showthread.php?p=3441752)). Guides advise putting frequent actions on face buttons, so they can be pressed while the left thumb steers. Rare cooldowns go on the D-pad. Splitting actions across expanded-hold sides is better than cycling sets with a bumper, which adds delay ([Icy Veins Dancer keybindings](https://www.icy-veins.com/ffxiv/dancer-keybindings)).

In WoW this becomes the following:

- Native emulation sets `GamePadEmulateShift=PADLTRIGGER` and `GamePadEmulateCtrl=PADRTRIGGER`.
- Holding LT produces `SHIFT-PAD1` and so on; holding RT produces `CTRL-PAD1`; holding both produces `CTRL-SHIFT-PAD1`.
- One `SecureHandlerStateTemplate` header with a driver such as `[mod:ctrl,mod:shift]3;[mod:ctrl]2;[mod:shift]1;0` flips the visible page.
- The header either re-points 8 child `SecureActionButtonTemplate` buttons' `action` attributes, or calls `self:SetBindingClick()` inside the restricted snippet. Both are legal in combat because Blizzard's secure code evaluates the driver ([SecureStateDriver.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_RestrictedAddOnEnvironment/SecureStateDriver.lua); [RestrictedFrames.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_RestrictedAddOnEnvironment/RestrictedFrames.lua)).

The addon needs no `OnUpdate` code. Showing and hiding the half that matches the held trigger is an alpha change. FFXIV offers the same with its "always display" off plus transparency setting ([consolegameswiki W Cross Hotbar](https://ffxiv.consolegameswiki.com/wiki/W_Cross_Hotbar)).

The compromise is press order. Native modifiers only report what is held, so LT→RT and RT→LT both resolve to `CTRL-SHIFT`. ConsolePort's repo spells out the limit: `[mod:]` drivers are resolved "against the modifiers physically held and cannot see a latched or doubled layer". That is why it carries a 946-line restricted-environment "Layers" state machine to track order, latches and double-taps ([Layers.lua](https://github.com/seblindfors/ConsolePort/blob/master/ConsolePort/Controller/Layers.lua)). FFXIV itself allows both orders to point at the same set, trading half the buttons for order independence ([Akhmorning](https://www.akhmorning.com/resources/controller-guide/the-cross-hotbar/)). The lean design should take that trade:

- LT, RT and LT+RT give three 8-slot layers, or **24 crossbar actions plus the unmodified face buttons, shoulders and stick clicks**. That is enough for most specs.
- WXHB double-tap stays out. FFXIV makes it opt-in, and timing windows add latency and ambiguity.
- A later phase can add `ALT` emulation on a bumper for a fourth layer before anyone builds an order-tracking state machine.

The difference between these 24 actions and FFXIV's 32 default actions is the cost of staying small. This conclusion is inferred from the native modifier model; it has not been tested in game.

The second decision is whether the crossbar draws its own buttons. Midnight makes `GetActionCooldown`, `GetActionCharges` and related action-bar queries secret during restricted states ([ActionBarFrameDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/ActionBarFrameDocumentation.lua)). Blizzard's stated rule is that combat information "can be displayed by addons but not known" ([Blizzard News](https://news.blizzard.com/en-us/article/24246290/combat-philosophy-and-addon-disarmament-in-midnight)). Custom buttons therefore have to pass secret values straight into Cooldown and StatusBar widgets and must never compare them in Lua. The safest MVP offers two modes. "Native bars" mode binds pad chords to Blizzard binding actions such as `ACTIONBUTTONn` and `MULTIACTIONBARnBUTTONm`, so Blizzard's own buttons, placed in Edit Mode, render cooldowns and glow with zero addon frames. "Crossbar" mode draws 8 lightweight `SecureActionButtonTemplate` buttons whose `action` slots point at the corresponding Blizzard bar slots. Pad glyphs come from the native atlases, and cooldowns are drawn only through secret-aware widgets. Both modes store actions in WoW's own action slots, so the addon never keeps an action database. That removes the need for LibActionButton and avoids repeating ConsolePort's "export stops at slot 120" class of bugs ([issues](https://github.com/seblindfors/ConsolePort/issues)).

## Targeting, cursor and settings should borrow FFXIV's ideas but WoW's machinery

Most targeting needs no runtime code. Soft-target CVars take `Enum.SoftTargetEnableFlags`, where Gamepad is 1 and Any is 3 ([SoftTargetConstantsDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/SoftTargetConstantsDocumentation.lua)). The native `INTERACTTARGET` binding calls `C_PlayerInteractionManager.InteractUnit("anyinteract")` ([Bindings_Standard.xml](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_FrameXML/Bindings_Standard.xml)). The preset should therefore:

- set `SoftTargetEnemy`, `SoftTargetFriend` and `SoftTargetInteract` (exact default values unverified);
- bind interact to a face button;
- bind `TARGETNEARESTENEMY` and its previous-target counterpart to D-pad left/right.

That last point copies FFXIV's default, where D-pad left/right cycles targets ([Official Game Manual](https://na.finalfantasyxiv.com/game_manual/operation/)). This also matches FFXIV's own advice to filter for enemies when the weapon is drawn ([SCUF](https://www.scufgaming.com/us/en/gaming/games/final-fantasy-14/final-fantasy-xiv-controller-settings/)). Lost Ark's mixed reception of forced auto-targeting argues for keeping any auto-target assist off by default ([MMORPG.gg](https://mmorpg.gg/mmorpgs-controller-support/)).

Healing is where FFXIV is weakest and where an addon adds the most. FFXIV players call D-pad party selection "always going to be a bit slower than F-keys" ([SE forum](https://forum.square-enix.com/ffxiv/threads/384784)). Its best idea is a **soft target that lasts one action**: D-pad up/down walks a wrapping party list, the next spell lands on the highlighted member, and Confirm promotes it to a hard target ([Akhmorning: Controller Targeting](https://www.akhmorning.com/resources/controller-guide/controller-targeting/)). The WoW equivalent is a stripped-down version of ConsolePort's raid cursor. That cursor is a secure handler that scans for frames carrying a `unit` attribute and, on PreClick, sets `unit` on target or focus buttons, with an option to route spells to the cursor unit ([Raid.lua](https://github.com/seblindfors/ConsolePort/blob/master/ConsolePort_Target/View/Cursor/Raid.lua)). The lean design narrows it:

- It scans only when group roster events fire, not on every frame show.
- It moves in a fixed, role-sorted order that wraps.
- It writes the selected unit into the crossbar buttons' secure `unit` attribute, so spells cast on it without changing the hard target.

The secure environment provides `UnitExists`, `PlayerCanAssist` and handle-level `SetAttribute`, so this works in combat ([RestrictedEnvironment.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_RestrictedAddOnEnvironment/RestrictedEnvironment.lua)). Ground targeting should stay with the engine. FFXIV's free reticle steering has no addon-level equivalent in WoW, so the native gamepad cursor and `@cursor`/`@player` macro options are the substitutes.

For menus, FFXIV pairs focus navigation with an opt-in virtual mouse (LB+R3) that is needed for drag-and-drop ([Official UI Guide](https://eu.finalfantasyxiv.com/uiguide/faq/faq-interface/interface_pad_mouse.html)). WoW already has the virtual mouse. ConsolePort's node-scanning interface cursor is the part to resist. It recursively scans frame trees, needs a per-Blizzard-addon hook file to stay usable ([Cursor.lua](https://github.com/seblindfors/ConsolePort/blob/master/ConsolePort_Cursor/View/Cursor.lua)), and is the likeliest cause of the Midnight secret-value taint reports filed against ConsolePort. Those include "550x secret number compares in Blizzard nameplate setup", secret arithmetic in tooltips and money frames, and `ConsolePort_Cursor` tainting numeric conversion ([GitHub issues](https://github.com/seblindfors/ConsolePort/issues)). The MVP should rely on the native cursor, which Blizzard already toggles for bags, loot and menus. A later, opt-in phase can add focus navigation for a fixed allowlist of frames: gossip and quest dialogs, loot, bags and the character pane. Even then, it should click only through paths that do not call `OnEnter` or `OnClick` handlers on Blizzard frames from addon code.

Settings and profiles are cheap wins. FFXIV's most important setup control is a single **Gamepad Mode toggle**. A common new-player failure is not switching it on ([Official UI Guide](https://na.finalfantasyxiv.com/uiguide/faq/faq-switch/control_gamepad.html); [Steam](https://steamcommunity.com/app/39210/discussions/0/1640926712947003326)). FFXIV also separates per-device settings (button icons, mapping, virtual mouse) from per-character play settings (hotbars, targeting). WoW's Settings API supports this directly through `Settings.RegisterVerticalLayoutCategory`, `RegisterAddOnSetting` and `SetupCVarCheckbox`, so no custom config frames are needed ([Blizzard_Settings.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_Settings_Shared/Blizzard_Settings.lua)). Bindings belong in WoW's native binding sets (Account or Character), written with `SetBinding`/`SaveBindings` as ConsolePort does ([Wrapper.lua](https://github.com/seblindfors/ConsolePort/blob/master/ConsolePort/Utils/Wrapper.lua); [KeyBindingsDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/KeyBindingsDocumentation.lua)). Blizzard's keybinding UI then remains a fallback editor.

FFXIV's weakest area is copying setups between characters, which players work around with file copying and third-party tools ([SE forum](https://forum.square-enix.com/ffxiv/threads/397915); [itch.io tool](https://sebastianscaini.itch.io/ffxiv-local-character-settings-copy-tool)). The addon should beat it with:

- one account table holding named profiles, defaulting to account-wide;
- optional per-character and per-spec overrides;
- "copy from character X";
- a plain import/export string.

For multi-user setups, where several people share an account or one person moves between a desk PC and a Steam Deck, named profiles cover play settings. Device-level CVars are stored locally, so a Deck and a desktop can differ. ConsolePort's Deck preset goes further and sets `synchronizeBindings=0` and `synchronizeConfig=0` to stop server sync overwriting device-specific bindings ([Deck.lua](https://github.com/seblindfors/ConsolePort/blob/master/ConsolePort/Model/Gamepad/Deck.lua)). The lean addon should offer that as an explicit, explained option, not apply it silently.

## Midnight's rules and Blizzard's own roadmap set the risk envelope

Midnight added secret values and an addon-restriction state machine with Combat, Encounter, ChallengeMode, PvPMatch, Map and Chat restriction types. Code can query these through `C_RestrictedActions.IsAddOnRestrictionActive` and the `ADDON_RESTRICTION_STATE_CHANGED` event ([RestrictedActionsConstantsDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/RestrictedActionsConstantsDocumentation.lua)). Comparisons or arithmetic on a secret value raise Lua errors. Helpers such as `issecretvalue`, `canaccessvalue` and `scrub` exist for defensive code ([FrameScriptDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/FrameScriptDocumentation.lua)). Input and secure actions were not removed, so an addon that only routes button presses to secure actions is largely unaffected. The exposure is in three areas: displays (cooldowns and auras on custom buttons), anything that touches Blizzard frames insecurely, and `SetCVar`, which refuses secret arguments and protected CVars ([CVarDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/CVarDocumentation.lua)). ConsolePort shows this is not hypothetical: an October 2026 issue reports `ADDON_ACTION_BLOCKED` from `SetCVar` during a settings refresh ([issue tracker](https://github.com/seblindfors/ConsolePort/issues)). The defensive rules follow:

- Write CVars and bindings only out of combat and only from user-initiated code. Queue anything requested in combat for `PLAYER_REGEN_ENABLED`.
- Use `hooksecurefunc` rather than replacing Blizzard functions.
- Never touch Blizzard secure frames' attributes.
- Treat every combat-derived number as potentially secret.

Programmatic clicks are also narrower than before. `type="click"` now refuses delegates that have access constraints or the ScriptedInput forbidden aspect ([SecureTemplates.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_FrameXML/SecureTemplates.lua)).

The resource budget is mostly avoided rather than optimized. `C_GamePad.GetDeviceMappedState()` returns a fresh table, so polling it in `OnUpdate` creates garbage every frame. The garbage claim is inferred from the API's return type. The ring should enable stick input only while it is open, using `EnableGamePadStick` and `OnGamePadStick`, which secure handles can toggle in combat ([SimpleFrameAPIDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/SimpleFrameAPIDocumentation.lua)). Everything else runs on events and Blizzard-evaluated state drivers. The client has a built-in profiler, `C_AddOnProfiler`, with `GetAddOnMetric` (session, recent-60-tick, encounter and peak averages) and `MeasureCall` (time plus bytes allocated). It also warns players when an addon crosses performance thresholds ([AddOnProfilerDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/AddOnProfilerDocumentation.lua)). The addon should read its own metric in a `/lp perf` command and keep the encounter average as a release-gate number. The specific gates, "zero `OnUpdate` scripts registered while idle" and "under 3k lines at MVP", are design targets, not measured baselines.

The strategic risk is **WoW: Forever**. Blizzard announced it at BlizzCon in September 2026 with native controller support labelled "Gamepad (Alpha)". Its radial-driven UI navigation works "fairly well out of the box", it launches on 2026-11-04, and Blizzard has not said whether retail will get it ([godisageek](https://godisageek.com/2026/09/wow-forever-xbox-controller-support/); [Blizzard feedback thread](https://us.forums.blizzard.com/en/wow/t/feedback-controller-support/2355361)). This argues for the lean approach. An addon built on native bindings and CVars can step aside, or detect and defer to native UI, at low cost. ConsolePort's replacement bars and menus would be stranded. ConsolePort already targets Forever (interface 16001) but has open Forever issues on look inversion and gamepad slot binding ([Const.lua](https://github.com/seblindfors/ConsolePort/blob/master/ConsolePort/Utils/Const.lua); [issues](https://github.com/seblindfors/ConsolePort/issues)). Forever compatibility is a reasonable later target and should not be an MVP commitment. The Classic branches share the gamepad and secure-template code ([classic GamePadDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/classic/Interface/AddOns/Blizzard_APIDocumentationGenerated/GamePadDocumentation.lua)), but it is unknown whether secret-value enforcement applies there. Two further gaps are open. Secret-value behaviour of binding calls in 12.x was not verified. The retail interface number for 12.1.5 is likely 120105; only 120100 for 12.1.0 is confirmed ([ConsolePort.toc](https://github.com/seblindfors/ConsolePort/blob/master/ConsolePort/ConsolePort.toc)).

Licensing determines how ideas can be borrowed. The ConsolePort suite is under the **Artistic License 2.0**, which allows modified redistribution under renaming and disclosure conditions ([LICENSE.md](https://github.com/seblindfors/ConsolePort/blob/master/LICENSE.md)). Its node-navigation library ConsolePortNode and its data layer RelaTable are **GPL v2**, so copying them verbatim makes the derived work GPLv2 ([ConsolePortNode.lua](https://github.com/seblindfors/ConsolePortNode/blob/master/ConsolePortNode.lua); [RelaTable.lua](https://github.com/seblindfors/RelaTable/blob/master/RelaTable.lua)). The cleanest route is to study the algorithms and write fresh code, with a distinct name. The algorithms worth studying are secure angle-to-index radial selection, secure unit-frame scanning and the binding-preset generator tables ([Xbox.lua](https://github.com/seblindfors/ConsolePort/blob/master/ConsolePort/Model/Gamepad/Xbox.lua)). The most compatible choice is to license the new addon GPLv2-or-later, which keeps the option to adopt ConsolePortNode later. Blizzard's UI source is a reference for API behaviour, not a code donor. None of this is legal advice.

## Recommended architecture and MVP scope

The architecture is one always-loaded addon (working name "LeanPad") of about six files, with no embedded libraries, no textures, and one optional load-on-demand ring module. **Setup** runs once on first login or from the Settings panel. It detects the device through `C_GamePad.GetActiveDeviceID` and `GetDeviceMappedState().labelStyle` to choose glyphs, sets `GamePadEnable=1`, assigns trigger modifier emulation, a cursor-click mapping and soft targeting, and writes a preset into the chosen binding set after a single confirm dialog. That is FFXIV's master toggle, plus "sensible default bindings that work immediately". **Bindings** apply static `SHIFT-/CTRL-/CTRL-SHIFT-PAD*` bindings. In crossbar mode they also apply override-click bindings owned by one secure header, the only owner of override bindings, which is the rule ConsolePort adopted after "two frames binding the same key fight over recency" ([repo](https://github.com/seblindfors/ConsolePort)). **Crossbar** is one state header and 8 secure buttons. **UnitCursor** is one secure handler. **Profiles** is one SavedVariables table plus a small serializer. **Settings** registers with Blizzard's panel. The table below sets the scope.

| Area | Build (MVP) | Lean on native | Drop or defer |
|---|---|---|---|
| Input and devices | Detect device, pick glyph style | SDL mapping DB, `GamePad*` CVars, emulated modifiers | Calibration, custom SDL configs |
| Bindings | One-click presets (Xbox/PS/Deck), combat-queued rebinds | Native binding sets, Blizzard keybinding UI as fallback editor | Order-aware chord layers, latches, double-tap WXHB |
| Action surface | 3-layer crossbar (LT, RT, LT+RT), hide-when-idle | Blizzard action slots, Edit Mode, cooldown rendering | Custom bar module, bar covers and art, LibActionButton |
| Targeting | Soft-target and target-cycling preset (MVP); wrap-around party/raid unit cursor routing spells via the secure `unit` attribute (Phase 2) | Soft target CVars, `INTERACTTARGET`, target-nearest bindings | Unit hotkeys ("EasyMotion"), target ring, ground reticle |
| UI navigation | Nothing custom | Native gamepad cursor and Blizzard auto-toggle | Node-scanning cursor (Phase 3, allowlist only), menu replacement, loot frame, radial keyboard |
| Settings and profiles | Master toggle, device/play split, named profiles, per-spec crossbar page map, copy-from-character, import/export string | Blizzard Settings API | Bespoke config UI, guided tutorial, QR export |
| Performance | `/lp perf` from `C_AddOnProfiler`, zero idle `OnUpdate` | Secure state drivers, events | Continuous `GetDeviceMappedState` polling |

The roadmap follows from that scope. **Phase 1 (MVP)** ships Setup, Bindings presets, the crossbar in both native-bars and crossbar modes, soft-target defaults and Settings and Profiles. A new player should be playing in under a minute, with zero always-running code. **Phase 2** adds the healer unit cursor, a single secure utility ring (mounts, hearthstone, consumables, auto-filled at setup), and an "auto-fill crossbar" that scans the spellbook once at setup and places rotation spells on face buttons and cooldowns on the D-pad, as FFXIV's XMapper plugin does ([FFXIVXMapper](https://github.com/AHAKuo/FFXIVXMapper)). The ring should be filled by drag-and-drop or auto-fill from the start, to avoid ESO's "not at all obvious how to add stuff to the new wheels" complaint ([ESO forum](https://forums.elderscrollsonline.com/en/discussion/607094/)). **Phase 3** is opt-in only. It adds an allowlisted focus-navigation cursor for dialogs, loot and bags, an `ALT`-emulated fourth layer, on-screen chord hints, and Forever and Classic TOC targets once their restrictions are verified. Every phase should end with a pass through `C_AddOnProfiler` in a raid encounter and a taint check with BugGrabber, because the Midnight error class that hurts ConsolePort is the one most likely to hurt a newcomer.

## Conclusion

ConsolePort can do much more than a lean addon, but most of that extra capability now duplicates what Blizzard ships or creates taint and secret-value exposure. Once the engine handles input, modifiers, cursor and soft targeting, the gap between a 59k-line suite and a 3k-line addon is mostly configuration UI, a replacement action bar, art, and an insecure interface cursor. In Midnight, the cheapest way to avoid errors is simply not to have those parts. The one real loss is order-sensitive chord layers, and FFXIV's own settings show that players accept collapsing them.

Building close to native also positions the addon well whatever Blizzard does with Forever's controller UI. If native retail controller support never arrives, a crossbar, a healer unit cursor and one-click setup cover the gaps players actually complain about. If it does arrive, an addon that writes only CVars and bindings can step back to just the unit cursor and ring. In both cases the measure of success is the same: a new player can start playing quickly, and the profiler shows near-zero cost in a raid encounter.
